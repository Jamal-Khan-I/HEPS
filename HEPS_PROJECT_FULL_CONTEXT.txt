1. SYSTEM OVERVIEW & CLINICAL MISSION
================================================================================
The Hospital Emergency Priority System (HEPS) is an enterprise-grade clinical
information management, real-time emergency triage, and dynamic hospital
resource routing application built for the Emergency Department (ED) of City
General Hospital.

In high-volume emergency departments, delays in triaging and attending to
critically ill patients often lead to preventable clinical deterioration, SLA
breaches, and avoidable mortality. Traditional ED software often functions
merely as a passive electronic record with hardcoded simulated data, lacking
algorithmic intelligence to prioritize care dynamically based on physiological
urgency, wait-time degradation, doctor workload, and bed availability.

HEPS solves this by integrating:
1. Rigorous Data Structures & Algorithms (DSA): Utilizing an in-memory binary
   Min-Heap (PriorityQueue) governed by a composite clinical priority comparator
   and an active wait-time escalation daemon that prevents patient neglect.
2. Objective Physiological Acuity (NEWS2): Automatic computation of the UK
   Royal College of Physicians National Early Warning Score 2 across all vital
   signs (SpO2, Heart Rate, Blood Pressure, Respiration Rate, Temperature, and
   Glasgow Coma Scale).
3. Hybrid AI Clinical Intelligence: A multi-agent clinical intake engine that
   extracts structured clinical data from natural language nurse narratives,
   recommends triage urgency levels, predicts medical specialties, and flags
   occult risks, all cross-validated against deterministic Java safety guardrails.
4. Deterministic Resource Routing: Automatic routing to on-duty specialist
   physicians based on clinical complaint and workload balancing, paired with
   physical bed allocation across 12 designated ED bays with sanitization timers.
5. Dual-Store Persistence: High-performance local MySQL 8.4 relational database
   with an automated daemon auto-recovery mechanism coupled with a configurable
   Google Firebase Realtime Database cloud sync connector.

3.1 MIN-HEAP EMERGENCY QUEUE SCHEDULING ALGORITHM
--------------------------------------------------------------------------------
The core of the emergency department priority scheduling is implemented in
`com.hospital.priority.service.QueueService` utilizing a Java Collections
binary Min-Heap (`java.util.PriorityQueue<Patient>`) parameterized with a custom
`PatientPriorityComparator`.

Algorithmic Invariants:
1. Heap Invariant: For every node `i` other than the root (index 0), the priority
   of the patient at parent `floor((i - 1) / 2)` is strictly higher than or equal
   to the priority of the patient at node `i`.
2. Time Complexities:
   - Insertion / Enqueue (`offer`): O(log N)
   - Peek Head (`peekNext`): O(1) instantaneous access to highest-priority patient
   - Remove / Dequeue Head (`serveNext`): O(log N) extraction and reheapify
   - Arbitrary Cancellation (`remove`): O(N) search + O(log N) reheapify
   - Full Sorted Snapshot (`getSortedSnapshot`): O(N log N) using Dual-Pivot
     Quicksort on an isolated ArrayList copy, ensuring thread-safe reads without
     mutating the live PriorityQueue.

Thread-Safety Model:
All queue operations (`enqueue`, `peekNext`, `serveNext`, `removeFromQueue`,
`checkAndApplyEscalations`, `getSortedSnapshot`) are guarded by `synchronized`
method locks on the singleton `QueueService` instance, preventing race
conditions during concurrent patient admissions, background triage scans, and
doctor attendances.

3.2 MULTI-TIERED PATIENT PRIORITY COMPARATOR ALGORITHM
--------------------------------------------------------------------------------
Implemented in `com.hospital.priority.model.PatientPriorityComparator`.
The comparator implements a deterministic multi-stage priority evaluation:

Algorithm Steps (`compare(Patient p1, Patient p2)`):
Step 1: Urgency Rank Evaluation
  Extract integer clinical rank of each patient:
    - CRITICAL = 1
    - HIGH     = 2
    - MEDIUM   = 3
    - LOW      = 4
  Lower numerical rank signifies higher clinical urgency.
  Comparison:
    `urgencyComparison = Integer.compare(p1.getRank(), p2.getRank());`
  If `urgencyComparison != 0`, return `urgencyComparison`.

Step 2: Tie-Breaker 1 - First-Come, First-Served (FIFO) Arrival Time
  If urgency levels are equal, the patient who arrived earlier must be seen
  first to minimize waiting duration and prevent queue starvation:
  Comparison:
    `arrivalComparison = p1.getArrivalTime().compareTo(p2.getArrivalTime());`
  If `arrivalComparison != 0`, return `arrivalComparison`.

Step 3: Tie-Breaker 2 - Deterministic Unique Token Ordering
  If both urgency rank and arrival timestamps are identical to the nanosecond,
  a strictly deterministic tie-breaker is applied using the patient token number:
  Comparison:
    `return p1.getTokenNo().compareTo(p2.getTokenNo());`

3.3 DYNAMIC SLA WAIT-TIME ESCALATION & HEAP RESTORATION ENGINE
--------------------------------------------------------------------------------
Patients left unattended in an emergency queue face clinical risk. To solve
the starvation problem inherent in static priority systems, HEPS implements a
dynamic SLA Wait-Time Escalation Engine in `QueueService.checkAndApplyEscalations()`.

SLA Target Thresholds by Urgency Level:
- CRITICAL : Immediate access (Target SLA: 0 min / Resus immediate)
- HIGH     : Target SLA: 15 minutes
- MEDIUM   : Target SLA: 60 minutes
- LOW      : Target SLA: 120 minutes

Escalation Transition Rules:
1. LOW Priority:
   If `waitMinutes >= 90`:
     - Escalated Level  : MEDIUM (Rank 4 -> Rank 3)
     - Flag `isEscalated`: TRUE
     - Escalation Reason: "Wait time reached Xm (Exceeded 90m threshold for Low priority)"
2. MEDIUM Priority:
   If `waitMinutes >= 45`:
     - Escalated Level  : HIGH (Rank 3 -> Rank 2)
     - Flag `isEscalated`: TRUE
     - Escalation Reason: "Wait time reached Xm (Exceeded 45m threshold for Medium priority)"
3. HIGH Priority:
   If `waitMinutes >= 25` and not already escalated:
     - Flag `isEscalated`: TRUE
     - Escalation Reason: "Prolonged High wait (Xm) - Immediate treatment recommended"

Heap Invariant Restoration (Re-Heapification):
Because Java's standard `PriorityQueue` does not automatically detect mutations
of internal element fields while items remain inside the heap array, modifying
a patient's `emergencyLevel` violates the heap ordering.
HEPS detects if any patient's status was changed during the scan (`heapModified == true`):
1. Captures all elements into a snapshot list: `List<Patient> currentList = new ArrayList<>(triageQueue);`
2. Clears the heap: `triageQueue.clear();`
3. Re-inserts each element: `triageQueue.offer(p);` (rebuilding the tree via binary sift-up operations)
4. Persists the updated priority levels, escalation flags, and audit reasons to MySQL.

3.4 NATIONAL EARLY WARNING SCORE 2 (NEWS2) PHYSIOLOGICAL ALGORITHM
--------------------------------------------------------------------------------
Implemented in `com.hospital.priority.service.NEWS2Service`.
Calculates the aggregate physiological score standardized by the UK Royal
College of Physicians across 6 physiological vital parameters and Glasgow Coma
Scale (GCS).

Parametric Point Allocations:

1. Respiration Rate (breaths per minute):
   - <= 8 breaths/min   : +3 points
   - 9 - 11 breaths/min : +1 point
   - 12 - 20 breaths/min: 0 points (normal)
   - 21 - 24 breaths/min: +2 points
   - >= 25 breaths/min  : +3 points

2. Oxygen Saturation SpO2 (%) - Scale 1 (Normocapnic / Standard):
   - <= 91%             : +3 points
   - 92% - 93%          : +2 points
   - 94% - 95%          : +1 point
   - >= 96%             : 0 points (normal)

3. Systolic Blood Pressure (mmHg):
   - <= 90 mmHg         : +3 points
   - 91 - 100 mmHg      : +2 points
   - 101 - 110 mmHg     : +1 point
   - 111 - 219 mmHg     : 0 points (normal)
   - >= 220 mmHg        : +3 points

4. Heart Rate / Pulse (beats per minute):
   - <= 40 bpm          : +3 points
   - 41 - 50 bpm        : +1 point
   - 51 - 90 bpm        : 0 points (normal)
   - 91 - 110 bpm       : +1 point
   - 111 - 130 bpm      : +2 points
   - >= 131 bpm         : +3 points

5. Body Temperature (Fahrenheit):
   - <= 95.0 F (35.0 C) : +3 points
   - 95.1 - 96.8 F      : +1 point
   - 96.9 - 100.4 F     : 0 points (normal)
   - 100.5 - 102.2 F    : +1 point
   - >= 102.3 F         : +2 points

6. Consciousness / GCS:
   - GCS == 15 (Alert)  : 0 points
   - GCS < 15 (Voice, Pain, Unresponsive / Confusion): +3 points

Aggregate Risk Classification:
- Total Score 0 - 4 : LOW Clinical Risk (Standard ward/ambulatory monitoring)
- Total Score 5 - 6 : MEDIUM Clinical Risk (Urgent clinical review, continuous telemetry)
- Total Score >= 7  : HIGH / CRITICAL Risk (Immediate emergency resuscitation)

3.5 DETERMINISTIC JAVA TRIAGE RULE ENGINE & SAFETY GUARDRAILS
--------------------------------------------------------------------------------
Implemented in `com.hospital.priority.service.JavaTriageRuleEngine`.
Functions as the authoritative, fail-safe safety guardrail of the triage process.

Key Safety Principle:
No probabilistic or AI language model is permitted to downgrade a patient whose
physiological parameters violate clinical danger thresholds. Even if AI suggests
LOW urgency, Java rules force an immediate escalation to CRITICAL.

Rule Hierarchy & Trigger Matrix:

Stage 1: Red Line Critical Thresholds
- Severe Hypoxemia     : SpO2 < 90%
- Severe Bradycardia   : Heart Rate < 40 bpm
- Extreme Tachycardia  : Heart Rate > 140 bpm
- Hypotensive Shock    : Systolic BP < 80 mmHg
- Hypertensive Crisis  : Systolic BP > 200 mmHg
- Extreme Respiratory  : RR < 8 or RR > 32 breaths/min
- Hyperpyrexia         : Temperature >= 104.0 F
- Life-Threat Symptoms : "cardiac arrest", "unresponsive", "choking",
                         "not breathing", "massive bleed", "gunshot"
Action: Immediate override to `EmergencyLevel.CRITICAL`.

Stage 2: High Urgency Conditions
- Moderate Hypoxia     : SpO2 90% - 94%
- Significant Tachy    : Heart Rate 115 - 140 bpm
- Severe Hypertension  : Systolic BP 180 - 200 mmHg
- High Fever           : Temperature 102.5 F - 104.0 F
- Acute Presentations  : "chest pain", "heart attack", "stroke", "paralysis",
                         "severe asthma", "breathless", "respiratory distress",
                         "open fracture", "uncontrolled bleed", "head injury"
Action: Assignment to `EmergencyLevel.HIGH`.

Stage 3: Medium Urgency Conditions
- Borderline abnormal vitals (checked via `Vitals.hasAbnormalVitals()`)
- Symptoms: "fracture", "deep cut", "stitches", "vomiting", "moderate pain",
            "sprain", "fever", "burn"
Action: Assignment to `EmergencyLevel.MEDIUM`.

Stage 4: Low Urgency
- Stable vitals and non-urgent complaints.
Action: Assignment to `EmergencyLevel.LOW`.

Specialty Determination Heuristic:
- Age <= 14                             -> PEDIATRICS
- Chest pain, cardiac, angina, rhythm   -> CARDIOLOGY
- Stroke, numbness, seizure, paralysis  -> NEUROLOGY
- Asthma, wheeze, breathlessness, lungs -> PULMONOLOGY
- Fracture, bone, dislocation, sprain   -> ORTHOPEDICS
- Gunshot, stab, vehicle accident, bleed-> TRAUMA_SURGERY
- All other general presentations       -> GENERAL_EMERGENCY

3.6 DOCTOR ROUTING & WORKLOAD BALANCING ALGORITHM
--------------------------------------------------------------------------------
Implemented in `com.hospital.priority.service.DoctorRoutingService`.
Ensures that admitted emergency patients are assigned to the most qualified,
available specialist with the lowest active patient workload.

4-Tier Routing Strategy:

Step 1: Available Target Specialist Match
- Query database for doctors where `specialty == targetSpecialty` and `status == AVAILABLE`.
- If candidates exist, execute workload balancing:
    `Doctor selected = min(candidates, comparingInt(Doctor::getCurrentWorkload).thenComparingInt(Doctor::getDoctorId));`
- Result: Exact specialty match with lowest active patient queue.

Step 2: Fallback to Available General Emergency Physicians
- If target specialists are all busy or off-duty, query doctors where
  `specialty == GENERAL_EMERGENCY` and `status == AVAILABLE`.
- Pick physician with lowest active workload.

Step 3: Fallback to Any Available Hospital Physician
- If General Emergency physicians are also fully occupied, query all hospital
  doctors currently marked `AVAILABLE`.
- Pick available physician with lowest active workload.

Step 4: All Doctors Busy (Queue Backlog Mitigation)
- If every single physician in the hospital is occupied (`BUSY`), search
  specialists in `targetSpecialty` regardless of busy status.
- Pick doctor with the least active backlog:
    `min(specialists, comparingInt(Doctor::getCurrentWorkload));`

Workload Lifecycle Synchronization:
- Upon Patient Admission: `doctor.incrementWorkload()` updates active count in MySQL.
- Upon Patient Discharge: `doctor.decrementWorkload()` decrements active count and
  restores status to `AVAILABLE` if workload drops below capacity threshold.

3.7 EMERGENCY BAY ALLOCATION, ZERO DOUBLE-BOOKING & SANITIZATION TIMER
--------------------------------------------------------------------------------
Implemented in `com.hospital.priority.service.BayService`.
Manages the 12 physical emergency resuscitation and observation bays.

Physical Bay Configuration & Zones:
1. Resus & Trauma (Critical Red Zone):
   - Bay 1 (Resus)  -> Dedicated for CRITICAL resuscitation
   - Bay 2 (Trauma) -> Dedicated for CRITICAL trauma surgery
2. Acute Care (Orange Zone):
   - Bay 3 (Acute)  -> Dedicated for HIGH urgency acute care
   - Bay 3b (Acute) -> Dedicated for HIGH urgency acute care
3. Monitored Observation (Yellow Zone):
   - Bay 4 (Obs)    -> Monitored cardiac/neurological telemetry
   - Bay 4b (Obs)   -> Monitored observation
   - Bay 7 (Obs)    -> Observation bed
   - Bed 8 (Obs)    -> Extended observation
   - Bed 9 (Obs)    -> Extended observation
   - Bed 10 (Obs)   -> Extended observation
4. Fast Track & Ambulatory (Green Zone):
   - Bay 5 (Fast track) -> Rapid minor injuries & pediatric assessment
   - Bay 6 (Ambulatory) -> Walk-in outpatient treatment

Concurrency & Zero Double-Booking Guarantee:
Bays are stored in a thread-safe `ConcurrentHashMap<Integer, Bay>`. State mutations
(`allocateBay`, `releaseBay`, `transferPatient`) use synchronized atomic validation:
- A bay cannot be allocated unless its status is strictly `BayStatus.FREE`.
- Releasing a bay transitions its state from `OCCUPIED` to `CLEANING`.

Automated Sanitization Countdown:
- When a patient is discharged, the bay enters `CLEANING` state with a timestamp.
- Default sanitization turnaround time: 3 minutes.
- `checkCleaningStatus()` runs on every query: if `now() - cleaningStartTime >= 3 min`,
  the bay automatically reverts to `BayStatus.FREE` and becomes available for intake.
- Manual override: Clinical nurses can click "Mark Cleaned Now" to bypass countdown.

3.8 MULTI-AGENT AI CLINICAL INTAKE & DISAGREEMENT DETECTION ARCHITECTURE
--------------------------------------------------------------------------------
Implemented in `com.hospital.priority.service.ai.*`.
Coordinates 4 specialized clinical agents and interacts with the AI service.

Multi-Agent Ensemble:
1. Intake Agent (`IntakeAgent.java`):
   Parses unstructured narrative notes entered by triage nurses. Extracts:
   - Patient demographics (name, age, gender, contact)
   - Vital signs (SpO2, Heart Rate, Blood Pressure, Respiratory Rate, Temp)
   - Chief complaint and pain score
   - Known drug allergies
   - Arrival mode (Walk-in, Ambulance, Referred, Police)
2. Triage Agent (`TriageAgent.java`):
   Evaluates clinical urgency against emergency medicine protocols. Generates:
   - Recommended emergency urgency level (CRITICAL, HIGH, MEDIUM, LOW)
   - Statistical confidence score (0.0 to 1.0)
3. Specialty Agent (`SpecialtyAgent.java`):
   Analyzes organ systems, symptomatic presentation, and patient history to
   determine optimal medical department.
4. Risk Agent (`RiskAgent.java`):
   Performs heuristic and NLP analysis searching for occult clinical deterioration:
   - Silent hypoxemia risks
   - Pre-shock index (Heart Rate / Systolic BP >= 1.0)
   - Atypical myocardial infarction presentations (e.g. diabetic females)
   - Sepsis screening criteria (SIRS)

Disagreement Detection Engine (`AIAgentOrchestrator.detectDisagreements`):
Cross-checks AI recommendations against `JavaTriageRuleEngine`:
1. Priority Conflict: If Java Rule Engine recommends higher urgency rank than AI,
   a safety guardrail flag is raised, logging the exact triggering physiological vitals.
2. Risk Conflict: If AI suggests LOW urgency but Risk Agent detects cardiac or
   pre-shock indicators, an automatic alert is dispatched to the clinician.
3. Department Conflict: Highlights variance between AI specialty prediction and
   rule-based mapping, allowing the clinical nurse to make an informed choice.

3.9 MASS CASUALTY INCIDENT (MCI) START TRIAGE ALGORITHM
--------------------------------------------------------------------------------
Implemented in `com.hospital.priority.controller.MassCasualtyController`.
Implements the Simple Triage and Rapid Treatment (START) protocol for mass-disaster
scenarios:

Step 1: Ambulatory Assessment
  Can the patient walk?
  - YES -> Classified as GREEN (Minor / Walking Wounded).
  - NO  -> Proceed to Step 2.

Step 2: Spontaneous Respiration Check
  Is the patient breathing spontaneously?
  - NO: Open airway manually.
        - Still not breathing -> BLACK (Deceased / Expectant).
        - Breathing resumes   -> RED (Immediate Resuscitation).
  - YES: Proceed to Step 3.

Step 3: Respiratory Rate Evaluation
  - RR > 30 breaths/min -> RED (Immediate).
  - RR < 10 or RR 10-30 -> Proceed to Step 4.

Step 4: Perfusion & Radial Pulse Assessment
  - Radial pulse absent OR Capillary refill > 2.0 seconds -> RED (Immediate).
  - Radial pulse present AND Capillary refill <= 2.0 seconds -> Proceed to Step 5.

Step 5: Mental Status Check
  Can the patient follow simple commands? ("Squeeze my hand")
  - NO  -> RED (Immediate).
  - YES -> YELLOW (Delayed / Urgent care).

3.10 PATIENT STATE MACHINE & CLINICAL LIFECYCLE
--------------------------------------------------------------------------------
Implemented in `com.hospital.priority.model.PatientStatus` and
`com.hospital.priority.model.PatientStateMachine`.

Strict Deterministic Transition Rules:
[REGISTERED] -> (Triage Completed)         -> [TRIAGED]
[TRIAGED]    -> (Enqueued to Min-Heap)     -> [WAITING]
[WAITING]    -> (Bed Allocated / Doctor)   -> [IN_TREATMENT]
[IN_TREATMENT]-> (Clinical Discharge)      -> [DISCHARGED]
[IN_TREATMENT]-> (Hospital Admission)      -> [ADMITTED]
[IN_TREATMENT]-> (External Transfer)       -> [TRANSFERRED]
[ANY ACTIVE] -> (Patient Mortality)        -> [DECEASED]

Validation Engine:
`PatientStateMachine.isValidTransition(currentStatus, nextStatus)` rejects illegal
state jumps (e.g., jumping from `REGISTERED` directly to `DISCHARGED`), throwing
an `IllegalStateException` and recording unauthorized attempts to the audit log.

--------------------------------------------------------------------------------
4.2 SELF-HEALING JDBC DAEMON CONNECTION RECOVERY
--------------------------------------------------------------------------------
Implemented in `com.hospital.priority.util.DBConnection`.
To prevent application crashes if MySQL is stopped after a Windows system reboot:
1. `getConnection()` detects `SQLException` when connecting to `127.0.0.1:3306`.
2. Inspects local filesystem for MySQL server binary:
   `C:/Program Files/MySQL/MySQL Server 8.4/bin/mysqld.exe`
3. If located, automatically launches `mysqld.exe` in the background via Java
   `ProcessBuilder` with `--defaults-file="C:/ProgramData/MySQL/MySQL Server 8.4/my.ini"`.
4. Polls localhost port 3306 with socket connections (up to 6 seconds) until the
   server begins accepting connections.
5. Retries the JDBC connection automatically, achieving zero-downtime self-healing.


--------------------------------------------------------------------------------
4.3 DUAL-STORE PERSISTENCE & FIREBASE CLOUD REALTIME SYNC
--------------------------------------------------------------------------------
Implemented in `com.hospital.priority.service.FirebaseService`.
HEPS operates a dual-store architecture:
- Primary Store: High-throughput local ACID-compliant MySQL 8.4 database.
- Cloud Realtime Sync: Google Firebase Realtime Database.
  - When enabled (`firebase.enabled=true` in `config.properties`), any update
    to patient priority, queue status, or bed allocation triggers an asynchronous
    HTTP `PUT`/`PATCH` to Firebase REST endpoints (`/patients/{tokenNo}.json` and
    `/queue/{tokenNo}.json`).
  - Allows mobile staff and remote administrators to view real-time department
    status without direct VPN access into the hospital's local network.
